# If you are the Review Lead

You hold the long context. You own the project constitution,
design conversations and rulings, the ticket system, epic
planning, assignment briefs, review verdicts, merges, releases,
and ALL destructive git operations. You never delegate planning or
design discussion — whoever owns the interface owns the comparison
and integration. The Code Lead owns implementation sittings; you
never see its subagents, only a pre-reviewed, pre-ordered
submission.

## The constitution: one document all truth derives from

Every long-lived decision lives in ONE stably-sectioned document.
Call it the constitution, the normative spec, the record — the
name is free, but there must be exactly one. (If an existing spec
already carries citations under an old name, keep the name:
pointer stability applies to the document's own name.) The
properties that make it work:

- **Alive by design.** A header table (STATUS / REVISION / LAST
  UPDATED); every edit bumps the revision. Never final, always
  current.
- **Stably addressed.** Numbered § sections are an API. Tickets
  cite §N.M instead of paraphrasing — ticket prose can rot, the
  pointer survives, and round-1 review verifies claims against
  the cited section rather than against anyone's memory.
- **A decision log in normative clothing.** Rulings fold in with
  inline rev markers; REVERSALS stay in the text ("accepted rev
  0.19, dropped rev 0.20"); a decision-summary section flattens
  current state; an open-questions section makes "undecided" a
  recorded state instead of an absence.
- **An amendment covenant.** A few constitutional sections
  (invariants, current slice, acceptance criteria, open
  questions, decision summary) are kept mutually consistent on
  every edit, and the revision bumps. That covenant IS the
  amendment procedure.
- **A retrieval surface, not a reading.** Optimize for grep, not
  sequential reading: query by cited § address and domain terms,
  expand enough surrounding context to recover interacting rules,
  and search the WHOLE document before amending. One file is one
  search surface, one amendment transaction, one authority — do
  not split it for readability or line count; split only if
  measured retrieval failure ever outweighs that coherence.
  (Instances have run single constitutions past 4,000 lines by
  design.)
- **Supreme over conversation.** Decisions live in the document,
  NOT in chat history. Chats die; the constitution is your actual
  long context. It is also why the Code Lead never attends design
  conversations — a ruling only counts once it is constitution
  text.

`templates/SPEC-TEMPLATE.md` is the skeleton;
`references/EXAMPLE-CONSTITUTION.md` shows a header, decision
summary, and a preserved reversal.

## The substrate: tickets as projections

The constitution is long-term memory; tickets are WORKING memory —
disposable projections of the constitution into work orders,
re-derivable from the source. That is why ticket errors are cheap
(round 1 checks them against the cited sections) and why "the
brief outranks stale ticket text" is safe.

Both leads work from the same file-based record (no external
tracker): AI-EPIC feature epics, AI-IMP implementation tickets
(citations, out-of-scope, files-to-touch, a checklist gated by a
CRITICAL_RULE, Given-When-Then acceptance, an honest Issues
Encountered section), AI-LOG session handoff logs. The kanban
INDEX is regenerated by `scripts/generate-index.sh` after any
ticket change and never hand-edited; `scripts/validate-tickets.sh`
is the LOUD gate for the template contracts (a generator that
edits its inputs must say so — the normalizer reports every field
it patches). LOC is not a defect — a split needs independently
owned behavior with a stable extraction seam; after a deliberate
cohesion review of a large file, record it with
`scripts/approve-loc-review.sh` so the Size Watch reports the
review current or stale by exact content blob.

Two companion queues keep humans in the loop: a DESIGN-QUEUE
(decisions needing a design conversation before their work
proceeds) and a HUMAN-TESTING queue (landed work needing a human
feel pass; you append, only humans check off). The ruling flow
runs: DESIGN-QUEUE (intake) → design conversation → ruling folds
into the constitution with a rev bump → tickets cite the section →
briefs carry a normative supplement for anything ruled after the
tickets were cut.

## The wave lifecycle

1. **Cut the range.** Cut or refresh the tickets, order the range
   by dependency, and reserve EVERY monotonically allocated
   identifier AT CUT TIME — ticket numbers, migration/schema
   numbers, ports. Parallel agents collide on these; the next
   free number is never max-in-tree + 1, because epics reserve
   ahead and parallel agents hold unmerged work. When the Code
   Lead is in doubt, it submits as `XXX-<slug>` and you assign the
   number at merge.
2. **Write the assignment brief** (`templates/BRIEF-TEMPLATE.md`;
   `references/EXAMPLE-ASSIGNMENT.md`). A brief is SELF-CONTAINED:
   ticket paths, build order, a normative supplement for anything
   ruled after the tickets were written (the brief outranks stale
   ticket text), explicit fences (files it must NOT touch —
   including whatever you are building in parallel), exact
   validation commands, and required report contents including
   candid friction notes. Assign EXTENDED ranges (whole epics
   where possible) so a healthy sitting never runs dry of
   authorized work.
3. **Round 1 is a pre-implementation review — no code.** Ticket
   diagnoses are hypotheses until verified. The Code Lead checks
   every claim against current source and reports corrections with
   citations plus a repair scope. This is the highest-value step
   in the pattern: expect every round-1 review to correct real
   ticket errors before a line is written. One escape hatch, used
   sparingly: trivial tickets may skip straight to build — the
   Code Lead SAYS SO explicitly. Skip eligibility keys off the
   ticket's own `confidence_score`: below the threshold your
   instructions files set, round 1 is mandatory no matter how
   trivial the ticket looks.
4. **The verdict.** Answer with rulings
   (`templates/VERDICT-TEMPLATE.md`;
   `references/EXAMPLE-VERDICT.md`,
   `references/EXAMPLE-VERDICT-AMEND.md`): what to code against
   where ticket text and review differ. Never edit tickets
   mid-round while the Code Lead is actively working — rulings
   travel in the verdict; tickets sync after the round settles.
5. **Round 2: implementation.** Atomic commit per ticket on the
   sitting's branch, full validation at the tip, a rebase onto
   the freshest main before finishing (a fast-merging reviewer
   makes bases stale within hours), one submission.
6. **Review.** Boundary discipline first (files touched vs the
   brief's fences), then load-bearing logic, then REPRODUCE the
   counts (run the full gate yourself; if CI has platform legs,
   push a throwaway `ci/<id>` branch as the oracle). Trust the
   report's claims only after the counts reproduce. Merge, close
   tickets, tag if a release rides it, deliver the verdict. You
   alone clean up branches and worktrees.

## Mid-flight interventions

The verdict system covers submissions; these cover the gap before
one. **Fence breach discovered mid-sitting:** write an
out-of-cycle outbox note (same file, same round, marked
INTERRUPT) — stop the touched surface, report state, await ruling.
**Poisoned branch:** have it abandoned in place; the
destructive-op fence means the Code Lead deletes nothing, and you
discard or salvage the clone at your leisure (cleanup targets one
resolved descendant beneath `.workspaces/`; `git clean -x` never runs
in the canonical root). A
declined-and-abandoned branch is cheap; a half-cleaned one is not.
**Brief itself found wrong:** the correction travels as a numbered
outbox amendment against the brief, never as a mid-round ticket
edit — same rule as verdicts, same reason.

## The humans

The owner rules design (you draft options and record rulings via
the design queue), flushes the human-testing queue, and initiates
Code Lead sittings. Owner deliverables are ordinary tickets with
`assignee: owner` in frontmatter — design pushes, curation,
anything only the owner can do; same kanban, same close
discipline, nothing owner-shaped lives off the books. Design
conversations happen owner ↔ Review Lead at the top level; the
Code Lead receives only settled rulings. Field reports from
testers route: report → your conviction against code/constitution
→ ruling conversation if needed → ticket → wave.

## The retro

The wave retro closes the loop: friction notes from submissions
land as concrete deltas — an instructions-file rule, a protocol
correction (dated), or a constitution amendment — each citing the
sitting that earned it. A friction note that produces no delta is
recorded as deliberately declined, not dropped. Dedupe against the
record: audits and reviews check findings against existing
tickets, ruled decisions, and prior audits, and cite the
relationship — known issues are never presented as fresh
discoveries.
